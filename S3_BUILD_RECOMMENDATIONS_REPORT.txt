          S3_STORAGE: BUILD RECOMMENDATIONS & ROADMAP REPORT

Scope: Concrete recommendations on what to build, what to avoid, and rollout order.

================================================================================
1. EXECUTIVE SUMMARY & HONEST ASSESSMENT
================================================================================
Your system currently excels at core S3 data-plane operations (buckets, objects,
prefixes, metadata, SigV4 gateway, SDK support) combined with distinct value-adds
(workspaces, RBAC, platform keys, audit trails).

To transition from a "custom blob store with an S3 gateway" to a robust, drop-in
S3 replacement, development should target tooling compatibility blockers first
(CLI/SDK probe actions, bulk operations), complete partially built features
(multipart upload gateway routing), and add core enterprise object management
(tagging and versioning).

Features involving multi-tier physical storage (Glacier) or distributed multi-region
infrastructure should be explicitly omitted at this stage.

================================================================================
2. PHASE 1: QUICK WINS — SDK & CLI COMPATIBILITY BLOCKERS
================================================================================
Effort: Low (hours to 1-2 days)
Impact: Eliminates common SDK/CLI runtime errors and enables seamless tooling.

1. HeadBucket & GetBucketLocation
   - Why: Standard tools (AWS CLI `aws s3 ls`, Boto3 `head_bucket`, Terraform)
     always probe bucket existence and region before executing operations.
   - What to build:
     * HEAD /{bucket} -> Returns 200 OK if bucket exists and user has access;
       404 NoSuchBucket / 403 Forbidden otherwise.
     * GET /{bucket}?location -> Returns standard XML:
       <LocationConstraint>us-east-1</LocationConstraint>

2. DeleteObjects (Batch / Multi-Object Delete)
   - Why: Recursive deletion commands (`aws s3 rm --recursive` or SDK bulk deletes)
     do not delete single items one-by-one; they send a batch POST request.
   - What to build:
     * POST /{bucket}?delete
     * Accepts XML payload with up to 1,000 `<Object><Key>...</Key></Object>` entries.
     * Performs atomic/batch deletion and responds with standard `<DeleteResult>`.

3. Complete Bucket CORS Round-Trip (GET & DELETE)
   - Why: Current backend automatically applies CORS on PUT, but tools reading
     or clearing CORS config encounter 404/405.
   - What to build:
     * GET /{bucket}?cors -> Return active CORS rules as XML.
     * DELETE /{bucket}?cors -> Reset or remove CORS rules.

================================================================================
3. PHASE 2: FINISH PARTIALLY IMPLEMENTED FEATURES
================================================================================
Effort: Medium
Impact: Unlocks large file uploads (>50MB to multi-GB) via standard AWS CLI/SDKs.

Gateway Multipart Upload Query Routing:
   - Current State: Backend primitives already exist in `rustfs.ts`
     (`createMultipartUpload`, `uploadPart`, `completeMultipartUpload`,
     `abortMultipartUpload`), but the HTTP SigV4 gateway lacks query parameter routing.
   - What to build:
     * POST   /{bucket}/{key}?uploads                -> CreateMultipartUpload (returns UploadId)
     * PUT    /{bucket}/{key}?partNumber={n}&uploadId={id} -> UploadPart
     * POST   /{bucket}/{key}?uploadId={id} (XML body)    -> CompleteMultipartUpload
     * DELETE /{bucket}/{key}?uploadId={id}                -> AbortMultipartUpload
     * GET    /{bucket}/{key}?uploadId={id}                -> ListParts
     * GET    /{bucket}?uploads                            -> ListMultipartUploads

================================================================================
4. PHASE 3: METADATA & ENTERPRISE COMPATIBILITY
================================================================================
Effort: Low to Medium
Impact: Essential for data classification, cost tracking, and SDK scripts.

Object & Bucket Tagging:
   - What to build:
     * Object: PutObjectTagging, GetObjectTagging, DeleteObjectTagging
       (`/{bucket}/{key}?tagging`)
     * Bucket: PutBucketTagging, GetBucketTagging, DeleteBucketTagging
       (`/{bucket}?tagging`)
   - Architecture:
     * Store as key-value pairs in Convex / relational schema.
     * Format responses as standard S3 `<Tagging><TagSet>...` XML.

================================================================================
5. PHASE 4: FLAGSHIP S3 CAPABILITY — VERSIONING & DELETE MARKERS
================================================================================
Effort: Medium to High
Impact: Prevents data loss, allows rollbacks, and satisfies enterprise compliance.

1. Bucket Versioning Configuration:
   - PUT /{bucket}?versioning & GET /{bucket}?versioning
   - Supported states: `Enabled` | `Suspended`.

2. Version-Aware Object Storage:
   - Store immutable versions keyed by UUID or timestamp.
   - Hard deletes become "Delete Markers" unless a specific VersionId is passed.
   - Support `ListObjectVersions` XML response.

================================================================================
6. HONEST ARCHITECTURAL BOUNDARIES: WHAT NOT TO BUILD
================================================================================
Do not invest effort in these features, as they add minimal value without
specialized underlying physical infrastructure:

1. Storage Classes (Glacier / Deep Archive / Intelligent-Tiering)
   - Rationale: Without distinct cold media (e.g. tape or separate archival clusters),
     faking storage classes inside a single disk or RustFS pool adds cognitive and
     code complexity with zero true storage savings.
2. S3 Select & Object Lambda
   - Rationale: High complexity to implement and maintain; modern analytical stacks
     favor client-side or distributed engines (e.g., DuckDB, Athena, Spark).
3. Cross-Region Replication & Accelerate Configuration
   - Rationale: Relevant only when maintaining geo-distributed data centers.

================================================================================
7. RECOMMENDED IMPLEMENTATION ORDER & TIMELINE
================================================================================
Step 1: Gateway Multipart Query Routing (Finishes existing engine work)
Step 2: HeadBucket, GetBucketLocation, and DeleteObjects (Quick compatibility wins)
Step 3: Object & Bucket Tagging (Simple metadata persistence)
Step 4: Bucket Versioning & Delete Markers (Flagship storage feature)
