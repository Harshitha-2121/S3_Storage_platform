Phase 3: Security Hardening & Rate Limiting (Afternoon 03:00 PM – 04:30 PM)
--------------------------------------------------------------------------------
- Token-Bucket Rate Limiting: 120 token burst, 30 req/sec refill rate per API key;
  bounded in-memory map to 5,000 entries to prevent memory exhaustion.
- Cryptographic Payload Integrity: Strict validation comparing computed SHA-256
  of incoming request bodies with `x-amz-content-sha256`. Rejects tampered payloads
  with HTTP 400 `XAmzContentSHA256Mismatch`.
- URI Sanitization: Rejection of path traversal sequences (`../`), encoded traversals
  (`%2F..%2F..%2F`), null bytes (`%00`), and backslashes (`\`) with 400 `InvalidURI`.
- Response Security Headers: Added `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`.

--------------------------------------------------------------------------------
Phase 4: Senior Security Re-Audit & Defect Fixes (Late Afternoon 04:30 PM – 06:00 PM)
--------------------------------------------------------------------------------
1. CRITICAL DEFECT IDENTIFIED & FIXED: Cross-Tenant CopyObject Bypass
   - Problem: Gateway forwarded `x-amz-copy-source` directly to upstream RustFS without
     validating that the source bucket belonged to the authenticated credential's account.
     Since RustFS proxies with root credentials, Tenant A could copy files out of
     Tenant B's private bucket into Tenant A's bucket.
   - Fix: Extracted `x-amz-copy-source`, authoritatively resolved the source bucket in
     Convex, verified `sourceBucket.accountId === cred.accountId`, enforced bucket scoping,
     and verified `s3:GetObject` permission.
   - Verification: Regression test confirmed that cross-tenant copy attempts are blocked.

2. PROTOCOL DEFECT IDENTIFIED & FIXED: Missing Byte-Range Support
   - Problem: `Range`, `If-Range`, and `Content-Range` headers were dropped, breaking
     S3 video/audio streaming and download resume.
   - Fix: Added transparent bidirectional forwarding of `Range`, conditional headers,
     `Content-Range`, and HTTP 206 Partial Content.
   - Verification: Verified exact byte-range slicing (0-9 and 10-19).

3. CACHE REVOCATION WINDOW HARDENING:
   - Tightened `CACHE_TTL_MS` from 60 seconds to 10 seconds. Revoked API keys or modified
     bucket permissions take effect within $\le 10$ seconds while preserving fast warm latency.
